# Multipos SaaS engineering audit

Date: 2026-09-27  
Audited commit: `d38235b` plus the uncommitted work listed in section 7  
Scope: application code, configuration, scripts, CI, dependencies, and every one of the 27 project-owned Markdown files that existed before this report. Dependency documentation under `node_modules` is third-party material and was deliberately excluded.

## 1. Executive assessment

This is a substantial, working multi-tenant SaaS POS, not a prototype. One React client and one Express/MongoDB API support four distinct retail verticals:

- Clothing: variants, branch stock, loyalty, suppliers, imports, exports, returns, and exchanges.
- Restaurant: tables, shifts, orders, kitchen tickets, refunds, categories, imports, and reports.
- Pharmacy: medicines, dated batches, prescriptions, expiry exposure, returns, imports, and reports.
- Super Shop: piece/weight sales, VAT-inclusive pricing, average costing, holds, exchanges, brands, imports, and analytics.

The strongest parts are tenant isolation, backend enforcement of permissions and plan limits, integer money handling, historical snapshots, idempotency on financial workflows, and the unusually broad HTTP regression suite. The project is maintainable, but it is not yet operationally mature enough for an unattended multi-instance production deployment.

## 2. Inventory and architecture

At the audit point the repository contained 654 tracked files, including 610 TypeScript/TSX/MJS files and approximately 100,029 source lines. There are 375 tracked server files, 240 client files, and 25 files under `docs/`.

### Runtime shape

```text
Browser / React 18 / Vite / TanStack Query
                 |
                 | JSON REST API + refresh cookie
                 v
Express 4 / Zod validation / auth + tenant + entitlement middleware
                 |
                 +-- shared account, wallet, subscription, import, return,
                 |   reporting, printing, payment, email, SMS services
                 |
                 +-- Clothing models and modules
                 +-- Restaurant models and modules
                 +-- Pharmacy models and modules
                 +-- Super Shop models and modules
                 |
                 v
MongoDB / Mongoose 8
```

An account owns a shared wallet and one or more workspaces. A workspace has one immutable POS vertical and one or more stores/branches. Tenant context is resolved on the server, store access is checked separately, and plan entitlements are read from server-owned subscription state. Client-supplied tenant, plan, price, balance, stock, and privilege fields are not trusted.

The project intentionally supports MongoDB without transactions. Correctness therefore depends on conditional updates, idempotency keys, reservation/claim records, and compensating writes. This design is well exercised, but it makes commit-point ordering especially important.

### Domain boundaries

| Concern   | Clothing                 | Restaurant           | Pharmacy              | Super Shop            |
| --------- | ------------------------ | -------------------- | --------------------- | --------------------- |
| Catalogue | Product + ProductVariant | MenuItem             | Medicine              | ShopProduct           |
| Stock     | Variant stock            | None                 | Dated MedicineBatch   | Per-branch ShopStock  |
| Ledger    | InventoryTransaction     | Not applicable       | PharmacyStockMovement | ShopStockMovement     |
| Sale      | Sale                     | RestaurantOrder      | PharmacySale          | ShopSale              |
| Returns   | Clothing return service  | Shared return engine | Shared return engine  | Shared return engine  |
| Costing   | Variant cost snapshot    | Not inventory-costed | Batch cost            | Weighted average cost |

Shared adapters are the right direction: they centralize tender validation, customer rollups, return figures, inventory restore behavior, imports, report printing, categories, and loyalty hooks without pretending all four businesses use the same stock model.

## 3. Correctness and security review

### Strong controls already present

- Monetary values are integers in minor units. Unsafe, fractional, negative, and over-ceiling inputs are rejected.
- Catalogue price, tax/VAT, cost, discount authority, change, and totals are computed by the server.
- Tenant and branch isolation are applied to both normal and hostile access paths.
- Vertical routes refuse tokens from another POS type.
- Sales keep product, variant, price, tax, cost, and staff snapshots so later catalogue edits do not rewrite history.
- Wallet, subscription, top-up, payment, import, held-sale, loyalty, return, and device workflows use conditional writes or operation keys to resist retries and races.
- Passwords are hashed; refresh tokens and payment-device secrets are stored as hashes; sensitive response fields are deliberately projected out.
- Uploads validate content rather than trusting the filename, enforce size/plan limits, and are included in quota accounting.
- Exports neutralize spreadsheet formula injection and omit credentials/secrets.

### Issues repaired during this audit

1. **Return commit ordering.** A return could be durably recorded and then reported as failed when a later stock, rollup, or loyalty update threw. The catch path could release the original claim, allowing a customer to retry an already-refunded return. Both the shared engine and Clothing engine now treat the Return record as the commit point: failures before it release reservations; failures after it are logged as critical repair work and never invite a duplicate refund.
2. **Return ledger identity.** Restored inventory now references the return id/number rather than the original sale id/number.
3. **Clothing card over-tender.** Non-cash overpayment could create change. The common rule is now enforced: change is permitted only when the cash portion covers it.
4. **Loyalty return model selection.** Releasing a failed return claim was hard-coded to Clothing's sale model. The release path now accepts the vertical sale model just like the claim path.
5. **Date validation.** Numeric coercion and impossible calendar dates could reach range endpoints, including a CI-dependent `from=0` case. Date input now requires an ISO-like date/date-time string or a Date and strictly validates date-only calendar values.
6. **Brand color configuration.** The primary color schema/property had been commented out, breaking type checking. It is restored, validates a CSS hex color, treats a blank value as absent, and the example quotes `#2056d5` so dotenv does not parse it as a comment.
7. **Test launcher portability.** The Windows test harness no longer launches `npm` through a shell. It calls the local TSX entry point and scripts using `process.execPath`, avoiding shell lookup failures and Node's unsafe-argument warning.
8. **Report-print test flake.** PDFKit embeds generation timestamps, so two correct PDFs can differ by a few compressed bytes. The regression now checks that the repeat is a complete PDF with a stable layout size instead of requiring an identical byte length.
9. **Dependency high severity.** Nodemailer was upgraded from 6.x to 10.0.10, removing the outstanding high-severity advisory.
10. **Tooling gates.** Format scripts now target the repository, CI fails on high/critical dependency advisories, and Dependabot is configured for weekly grouped npm updates.
11. **Test upload isolation.** Upload tests now write to a unique operating-system temporary directory and remove it during teardown; the root local-upload directory is also ignored so development files do not appear as source changes.

### Open risks, prioritized

#### P1 — address before multi-instance or high-volume production

1. **No durable post-commit reconciliation.** Return post-commit stock, customer, sale-rollup, and loyalty updates are best effort and emit critical logs. This prevents duplicate refunds, which is the correct safety direction, but a transient database failure can leave derived state stale. Add a persistent outbox/repair record, idempotent repair workers, an operator view, and failure-injection tests.
2. **In-process subscription scheduler.** The source explicitly describes the scheduler as single-instance. Running multiple API nodes can duplicate work and create unnecessary races, even though many money paths are idempotent. Use a database lease or external queue/scheduler before horizontal scaling.
3. **Integration credentials are plaintext at rest.** The platform SMTP password and SMS API key are hidden by default query projection but stored as plaintext in MongoDB. Encrypt them using an application/KMS-managed key, record key versions, and support rotation. Query projection prevents accidental disclosure; it is not encryption.
4. **Tax semantics need a product decision.** Clothing uses the store tax setting while other verticals implement their own behavior (for example, Super Shop product-level VAT included in price). The shared `Store.tax` field is therefore potentially misleading outside Clothing. Document and enforce vertical-specific semantics or replace it with an explicit per-vertical configuration contract.

#### P2 — next engineering cycle

1. Move the browser access token out of local storage if feasible. The HTTP-only refresh cookie is good, but an XSS bug can currently read the access token. A cookie-only/BFF design or in-memory access token narrows the blast radius.
2. Plan React Router 7 and ExcelJS replacement/migration work. `npm audit` reports four moderate advisories: direct `react-router-dom` and `exceljs`, plus transitive `react-router` and `uuid`. The available automated fixes are breaking and should not be applied blindly.
3. Upgrade Multer 1.x to Multer 2 and explicitly map upload limit errors to a normal client error without logging them as “Unhandled error.”
4. Split environment access into the validated configuration registry. Payment/SMS providers still read some `process.env` values directly, weakening startup validation and configuration discoverability.
5. Add structured request ids and propagate them through payment, wallet, return, email, and job logs. Critical repair logs must be searchable and alertable.
6. Break the 11k-line smoke suite into domain suites with shared fixtures. Add unit tests for money/date/return state machines and component tests for critical checkout behavior. Keep the full HTTP suite as the release gate.
7. Add a real browser pass for checkout, printing, barcode scanning, and the newest Super Shop screens. HTTP coverage cannot verify rendering, focus/scanner behavior, browser print CSS, QZ Tray, or physical printer integration.
8. Define a timezone per store/workspace and use it consistently in daily dashboards, receipts, jobs, and exports. Current behavior largely follows a configured/server business timezone rather than a first-class store timezone.
9. Remove tracked generated/editor artifacts such as `client/tsconfig.tsbuildinfo` and `.claude/launch.json` from history after confirming nobody relies on them.
10. Refactor the largest UI/service files (`PlatformPage`, `WorkspacePage`, report and vertical services, and the API endpoint registry) around cohesive features. They are still workable but raise review and regression cost.

#### P3 — documentation and maintainability

1. Rename the root package from `clothing-pos` and complete the README/API/database rewrite around the four-vertical product.
2. Resolve the existing Prettier backlog in a dedicated mechanical change. The formatter command is now real, and therefore correctly reports widespread pre-existing formatting differences.
3. Add an architectural decision record for standalone-Mongo compensating writes versus a required replica set/transactions deployment.
4. Add ownership/runbooks for dependency updates, failed background jobs, payment reconciliation, restore drills, and secret rotation.
5. Keep intentional vertical differences explicit. Data export is universal but its safe registry is vertical-aware; supplier management serves Clothing and Super Shop, while reports and taxation differ by vertical. “Shared” should not be confused with “identical.”

## 6. Recommended delivery sequence

1. Build the durable post-commit reconciliation/outbox for returns first. It closes the most important remaining correctness gap created by operating without transactions.
2. Encrypt SMTP/SMS credentials and write the rotation runbook.
3. Add scheduler leasing and request/job correlation before deploying more than one API instance.
4. Decide and document tax/timezone semantics per vertical; then encode them in validated configuration.
5. Split the regression suite and add failure-injection plus browser tests without reducing the existing release coverage.
6. Perform the React Router/Multer/Excel dependency migrations as isolated, tested changes.
7. Consolidate the README, API/database map, and return architecture; then do the mechanical Prettier cleanup.

New feature work should continue only when it preserves the existing invariants: server-owned pricing and permissions, integer money, tenant/store/vertical scoping, historical snapshots, idempotent external/financial operations, and a durable commit point that never asks a user to retry a transaction that may already have succeeded.
