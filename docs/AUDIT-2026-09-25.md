**Date:** 2026-09-25 · **Commit:** `c8de88d` (`main`, clean tree)
**Scope:** the ~22,000 lines across 248 files added after `AUDIT.md` (commit `bd7123d`),
plus the status of every finding that audit left open.

## Why this exists

`AUDIT.md` is dated 2026-09-24 but was written against `bd7123d`. Twenty commits
landed after it — the whole universal-POS programme (`docs/UNIVERSAL_POS_PLAN.md`
tasks 01–12: printing, date ranges, POS customers, split payment, the tender
service, out-of-stock sale, the inventory seam, returns, loyalty, categories,
import, report printing). None of that code has been reviewed. This audit covers
it and re-checks the old findings.

**Verified this run:** `npm run typecheck` clean (server + client) ·
`npm audit` → 1 high, 8 moderate. The E2E suite was not run (needs MongoDB).

## Verdict on the new code

The universal layer is better engineered than most of what it replaced. The
things that are easy to get wrong in a multi-tenant POS are right:

- **Tenant scoping is unconditional.** Every query in `posImport.service`,
  `posCategories.service`, `posLedger`, `posReturns.figures` and the four
  returns adapters carries `tenantId` (and `storeId` where the data is
  branch-scoped), via a private `scope(ctx)` or an explicit filter. No query
  in the new code takes an id from the request body.
- **`settleTender` is the real fix for the old M6.** The three duplicated
  checkout blocks are gone; the discount check, the enabled-method check, the
  shortfall and the cash-change rule now live in
  `services/pos/paymentMethods.service.ts` and all three newer verticals call
  it. Clothing uses the same primitives.
- **Returns hold quantities with a compare-and-swap** before touching stock, and
  release them on any failure — correct for a deployment without transactions.
- **Loyalty reversal is proportional and idempotent**: `returnTargets` prorates
  by returned value, claimed through a CAS on the sale, so a partial return
  reverses a partial share and a double-submit reverses nothing twice.
- **Money stays in integer minor units** throughout, including the proportional
  discount refund and the inclusive-VAT extraction in Super Shop.
- `ReturnModel`'s unique index on `idempotencyKey` is partial on
  `{$type:'string'}`, so the new code writing `null` cannot collide.

The findings below are the exceptions.

## New findings

### N1 (Medium) — a return can be recorded while the sale says nothing was returned

`services/returns/posReturns.service.ts:110-178`

The create path runs: reserve → restock → **write the `Return`** →
`applyReturnTotals` → `reverseLoyalty` → `applySaleStats`. The `catch` releases
the held quantities and rethrows — but by then the `Return` document is already
committed, and the restocked inventory is not reversed either.

If `applyReturnTotals`, `reverseLoyalty` or `applySaleStats` fails (any transient
write error), the result is:

- a `Return` row that every "net" report counts — `returnFiguresFor` and
  `returnsByDay` both read `ReturnModel` directly, so revenue and profit drop;
- a sale whose `returnedQuantity` was just rolled back, so **the same lines can
  be returned again** for the same money;
- stock that was put back once per attempt.

The method's own docstring claims "a sale can never end up with goods marked
returned that were never refunded" — true, but it is the opposite direction that
is unguarded: goods refunded that are not marked returned.

*Fix:* move the `ReturnModel.create` to the end of the sequence, or compensate it
(delete the return and re-decrement stock) in the `catch` alongside the release.

### N2 (Medium) — `store.tax` is still ignored in three of four verticals

Old finding M5, re-verified and now sharper. The string `tax` does not appear at
all in `restaurant.service.ts`, `pharmacy.service.ts` or `supershop.service.ts`.
All three compute `totalMinor = subtotal − discount − loyaltyDiscount`
(`restaurant:538`, `pharmacy:335`, `supershop:336`). Only
`sales.service.ts:516` applies `StoreModel.tax`.

Super Shop is a partial exception with its own **inclusive** per-product
`vatRateBps` (`supershop:353`) — which is a different mechanism, not the branch
tax setting. Restaurant and Pharmacy have no tax of any kind.

A merchant who switches on VAT in branch settings undercharges every Restaurant
and Pharmacy sale, silently, with the setting still showing as enabled. Either
apply it or hide it per vertical — the current state is the worst of both, and
it is the one place the universal programme did not reach.

### N3 (Low) — `releaseReturnClaim` is hardcoded to the Clothing model

`modules/loyalty/loyalty.service.ts:576-582`

`claimReturn` correctly takes a model parameter so any vertical can pass its own
sale collection. Its counterpart `releaseReturnClaim` does not — it writes to
`SaleModel` unconditionally. Not live today: only `returns.service.ts` (Clothing)
calls it, and `posReturns.service` never does. It becomes a silent no-op the day
a vertical needs to undo a claim. Give it the same parameter.

### N4 (Low) — Clothing skips the cash-change rule on one payment path

`modules/sales/sales.service.ts:626-635`

The three newer verticals enforce all three tender rules through `settleTender`.
Clothing calls `assertMethodsEnabled` and `assertCovered` but never
`assertChangeIsCash`. On the final fallback branch — no `cashTenderedMinor`, not
an exchange — `payments` summing above the total yields `changeMinor > 0` with no
cash row required, so an over-tendered card or bKash payment books change out of a
card. The earlier branches guard this; this one does not. Reachable directly
through the API.

### N5 (Low) — the same refusal answers 400 or 422 depending on vertical

`services/pos/paymentMethods.service.ts:90-130`. `POS_TENDER_DIALECT` and
`CLOTHING_TENDER_DIALECT` deliberately differ in status code and wording for
identical conditions. The code documents this as intentional and defers it to
plan task 03. Flagged only so it is a decision on the record, not a surprise to
an API consumer.

## Checked and found clean

- **Responsiveness (rule 14).** The unwrapped `<table>` elements in
  `PharmacyReportsPage`, `SupershopReportsPage` and `SaleDetailDialog` are
  `w-full` with no minimum width, so they compress rather than overflow. The
  fixed-width tables all pair `min-w-[…]` with an `overflow-x` wrapper. The
  remaining `w-[…]px` hits are thermal receipts, where fixed width is the point.
- **Report printing** (`services/reports/reportPrint.ts`). Filename sanitised,
  PDF written through the export module's writer so money formatting and
  formula-guarding stay in one place, errors handled after `headersSent`.
- **Import upload** (`modules/posImports/posImports.routes.ts`). Extension *and*
  MIME checked, memory storage, size and file-count limits, rate limited,
  entitlement + permission gated.
- **Route guards** on every new module: `authenticate → resolveTenant →
  requireVertical → requireSubscribedAccess → requirePermission`.
